Give ParseThreadsArg a testable failure mode

sim.cc:32–64

Before

sequenceDiagram participant Caller participant Parse as ParseThreadsArg participant Proc as process Caller->>Parse: (argc, argv) Parse->>Parse: validate Parse--xProc: exit(1) Note over Proc: caller and any

After

sequenceDiagram participant Caller participant Resolve as ResolveThreads Caller->>Resolve: (argc, argv) Resolve->>Resolve: validate Resolve-->>Caller: value | error Note over Caller: main logs + exits.
a test just asserts.

Problem

The interface's failure mode is exit(1) — invisible at the call site and fatal to whatever process calls it, so the validation logic (blank flag, non-numeric, over-core-count) can only be exercised by running the whole binary and reading stderr.

Solution

Return the parsed count or an error (e.g. a small variant, or throw and let main catch) instead of calling exit inside the module. main becomes the thin adapter that logs and exits; the module stays deep but its interface stops lying about what a caller can observe.

  • Deletion test: the validation rules don't disappear, they'd have to be reinvented in main — this module earns its keep, it just hides its exit at the wrong seam
  • Leverage: same validation, callable from a unit test with no Geant4 runtime
  • Locality: every "what counts as a valid thread count" question answered in one place, including in a test

Problem

The thread count → run-manager-type decision and the "macro/" + argv[1]-or-beam.in fallback are plain statements sitting inside main, interleaved with G4RunManagerFactory calls. There is no seam a test can enter through — exercising "what macro file do we pick" means running the batch executable.

Solution

Pull the decisions into a pure ResolveRunConfig(argc, argv) returning a small struct (run-manager type, thread count, macro path). main calls it once, then does Geant4 wiring — unconditionally, no branching left to get wrong.

  • Leverage: dnachem-min has no unit-test harness yet (per the CTest tickets in .scratch/geant4-testing/) — this is a natural first module that doesn't need a Geant4 runtime to test at all
  • Locality: the "which macro, how many threads" question moves from a scan of main to one function signature
  • main shrinks to two calls: resolve, then wire

Problem

GUI and batch are two real adapters of "how the run executes" — two adapters justify a seam — but today they're an inline if/else in main with manual new/delete resource management duplicated in the GUI branch only.

Solution

A small Run(mode, UIManager) seam with an interactive adapter and a batch adapter, each owning its own resource lifetimes.

Tension: CLAUDE.md asks for no abstractions beyond what the task needs, and useGUI is a single hardcoded compile-time flag flipped by hand, not a runtime choice. Worth doing only if GUI mode sees real use beyond occasional interactive debugging — otherwise the interface being introduced would have exactly one caller per binary, which is a hypothetical seam, not a real one.

Top recommendation

Extract the RunConfig resolver (Candidate B)

dnachem-min has no unit-test harness yet — only full-binary macro runs. ResolveRunConfig would be the first module in the project testable without a Geant4 runtime at all, and it directly de-risks the CLI/thread-count logic the project is already worried about getting right (per the CTest ticket series). Pair it with Candidate A so the resolver's own failure paths are assertable, not just its happy path.
